# RIMS/CRIS best practices for a small research unit: workflow and UX/UI

- **Date:** 2026-09-09
- **Author:** research agent (Claude)
- **Scope:** workflow, validation UX, self-service and public-surface design for a ~185-researcher / ~365-output research unit (UNIDCOM, IADE / Universidade Europeia). Stack assumed: Flutter web portal + Supabase, ORCID sign-in, admin approval queue, nightly Hugo public site. Enterprise features (grants, HR sync, bibliometrics) are out of scope.
- **Method:** primary sources only (standards bodies, vendor help centres, FCT/CIÊNCIAVITAE official documents, W3C, NN/g, GOV.UK, USWDS). All URLs fetched 2026-09-09. Claims without a primary source are marked `[unverified]`. Pages that refused automated fetch (HTTP 403) are marked; content for those comes from search-engine excerpts of the same URL.
- **Citation key:** `[Sn]` links to the numbered entry in section 6.

**BLUF.** (1) Every production CRIS starts an output record from an identifier lookup (DOI, Scopus/WoS ID, ORCID), not from a blank form; the researcher then *claims or rejects* candidates ([S18], [S27], [S32], [S41]). A blank form should be the fallback path, not the default. (2) The standard validation model is three states, draft → for validation → validated, moved by the creator and then by an editor/validator; Pure additionally gates "validated" on publication status ([S19]). The state must be visible to the researcher, not only in the admin queue ([S43] heuristic 1, [S52], [S53]). (3) De-duplication is done *at entry*: identifier match first, then ≈80 % title similarity, with a warning the submitter must acknowledge ([S21], [S22], [S35]). (4) For FCT the unit-level facts that matter are: every team member has a CIÊNCIA ID; every integrated PhD researcher has a CIÊNCIAVITAE that is filled, in English, and at public/semi-public visibility; the unit nominates its five most representative contributions with full text ([S15]). FCT explicitly prefers "most significant production" over exhaustive lists or bibliometrics ([S14]). The RIMS should model those flags, not h-indexes. (5) ORCID is both the vocabulary researchers already know and the sync backbone: CIÊNCIAVITAE↔ORCID synchronisation covers exactly Produções and Projetos ([S12], [S13]), so an output pushed to ORCID reaches CIÊNCIAVITAE without a separate integration. ORCID's minimum requirements forbid typed-in iDs and require the iD icon and full URL on display ([S8], [S9]).

## 1. What a RIMS/CRIS is and who defines it

**euroCRIS / CERIF.** euroCRIS maintains CERIF, "the comprehensive information model for the domain of scientific research", designed "to support interchange of research information between and with CRISs" ([S1]). The model has base entities *Person*, *OrganisationUnit* and *Project*; result entities *ResultPublication*, *ResultPatent* and *ResultProduct*; link entities that carry the relationships, e.g. *Person_OrganisationUnit* and *Person_ResultPublication*; and a semantic layer of classification schemes that types the links ([S1]). Vocabularies are published as RDF under `https://w3id.org/cerif/vocab/`, a CERIF API 1.0 specification exists, and euroCRIS notes an "upcoming CERIF refactoring project" under its new Technical Committee for Interoperability and Standards ([S2]). Practical implication: a person–output relationship is a first-class row with a role and dates, not a foreign key on the output.

**CASRAI dictionary.** The CASRAI dictionary is a controlled vocabulary for research-administration terms, "release v2026.1" with "1858 definitions across 29 thematic domains", stable per-entry URIs at `https://casrai.org/dictionary/term/<slug>`, CC-BY 4.0, and "123 structured business objects — Award, Book, Conference Paper — for CRIS and RIM integration" ([S3]). euroCRIS announced it is taking over management and curation of the CASRAI catalogue of elements ([S4]). Use it as the source of output-type labels rather than inventing local ones.

**OpenAIRE Guidelines for CRIS Managers.** Version 1.2.0 (June 2023, doi:10.5281/zenodo.8050936) defines a CERIF-XML profile exposed over OAI-PMH with metadata prefix `oai_cerif_openaire`; entities are Publication, Product, Patent, Person, OrgUnit, Project, Funding, Service, Equipment, Event and Medium, each top-level entity with its own OAI set ([S5], [S6]). Identifier support is required: ORCID for persons, DOI for publications, GrantDOI for funding; v1.2.0 relaxed the rule so "unmanaged entities" may lack an internal identifier ([S5]). This is the interoperability target if UNIDCOM ever wants its outputs aggregated by OpenAIRE.

**ORCID Collect & Connect.** ORCID's integration programme defines five badges, Authenticate, Display, Collect, Connect and Synchronize, under the principle "Enter once, reuse often"; Authenticate and Display are the baseline every integration must meet, Connect/Collect and Synchronize require the Member API ([S7]). The minimum requirements for member integrations are: "Collect authenticated ORCID iDs using OAuth", "Do not allow users to search or manually enter their ORCID iD", "Store the Name, ORCID iD and access token", "Do not request users change their visibility settings", and display the iD per the display guidelines ([S8]). Display guidelines: the iD "should always be accompanied by an ORCID iD icon", the full `https://orcid.org/…` URL is the preferred link form, and unauthenticated iDs must use the unauthenticated icon plus "(unauthenticated)" ([S9]). Record items carry a *source* and one of three visibilities (public, trusted parties, only me); an API client can only update or delete items it created, identified by *put-code*, and any visibility value sent by the API "will be ignored" ([S10], [S11]).

**FCT and CIÊNCIAVITAE.** FCT's R&D-unit evaluation regulation states that assessment "privilegiará a qualidade e não a sua quantidade" and that units "serão chamadas a identificar a produção científica que considerem mais significativa, em detrimento da exibição de listas exaustivas de publicações ou referências a indicadores bibliométricos", citing DORA and the Leiden Manifesto ([S14]). In the 2023/2024 exercise the application ran in three phases (unit registration, team registration, unit application); "todos os membros da equipa … têm de possuir CIÊNCIA ID"; integrated PhD researchers "têm de ter obrigatoriamente o curriculum CIÊNCIAVITAE preenchido" and "é essencial que o CIÊNCIAVITAE esteja em língua inglesa"; "A FCT apenas terá acesso aos dados do CIÊNCIAVITAE cujo nível de acesso seja semipúblico ou público"; nuclear CVs additionally submit a narrative CV; the unit indicates its "5 contribuições mais representativas" and supplies full text of its most representative publications ([S15]). Team lists are imported from FCT's "Plataforma de Atualização Permanente de Equipas de Unidades de I&D" at the start of team registration ([S15]). The evaluated activity period was 1 Jan 2018–31 Aug 2023 and 336 units were assessed by 29 panels ([S16], [S17]). CIÊNCIAVITAE is "desenvolvido e gerido pela FCT"; registration requires a CIÊNCIA ID; synchronisation with ORCID is bidirectional and "ocorre apenas nas áreas funcionais Projetos … e Produções"; records have three privacy levels (Público, Semi-público, Privado) and only "Público" records are published ([S12]). The FAQ describes synchronisation as two actions, "Adicionar ao CIÊNCIA VITAE" (pull works from ORCID) and "Adicionar ao ORCiD" (push new works), and lists five importers in the import assistant, including ORCiD, SciPROJ, RCAAP and PRIES ([S13]).

## 2. Workflow patterns across real systems

Short notes per system, then a summary table. "Not documented publicly" means no primary page was found on 2026-09-09.

**Elsevier Pure.** Automated search runs against enabled online sources using "the authors' names on publications, or ORCID/Scopus IDs, depending on the source"; hits appear as *import candidates* that the researcher can accept and import; the resulting task "is a mandatory task and can not be toggled off", email notification is optional ([S18]). Research-output workflow steps are "Entry in progress", "For approval"/"For validation" and "Validated", performed by Creator, Editor and (4-step) Validator roles, with an optional detached Administrator role; an admin rule can require that "only Research outputs with the publication status Published can be moved all the way to the 'Validated' workflow step" ([S19]). On manual import Pure warns "Similar title already exists" or "Publication is already imported" (source-ID match) and refuses re-import ([S21]). Editors find duplicates via "Duplicate title, ISBN or DOI" and may merge only records of the same content type ([S20]); the automatic deduplication job matches research outputs on title (80 %), DOI, ISBN, authors, year and pages, and persons on names with non-contradicting Scopus/ORCID IDs ([S22]). Visibility levels are Public, Campus (IP-restricted), Backend and Confidential; only Public reaches the Pure Portal ([S23], [S26]). Reporting is a separate module with data tables, data stories, shareable workspaces and snapshots; "Any user who should be able to do reporting must have a reporting role" ([S24], [S25]).

**Clarivate/Ex Libris Converis.** An "Automatic publication matcher" will "Automatically extract new publications from Web of Science and match them to your researchers"; reporting is via "embedded reports … in addition to advanced reporting options and dashboards via Converis Research Analytics" ([S27]). Modules include "Publication import" and "Push for validated publications from Converis to ORCID"; a Research Portal is the "Showcase for research outputs"; workflows are configurable "per entity, user rights per user role and workflow step"; web services expose "data marked as public" ([S28]). Release 6.18 documents a workflow matrix with a per-role status-comment field and fixes to the deduplication function and the auto publication importer ([S29]). The import actions "Import and relate to you", "Possible duplicate – needs validation", "Already your publication" are described only in a consortium page `[unverified: [S30] is not a vendor document]`.

**Symplectic Elements.** Harvests from "PubMed, Web of Science, Scopus, Crossref, Dimensions, ORCID" and others; offers "automatic claiming and identifier search"; a Reporting Hub with "highly configurable dashboards and reports" and "a specialist SQL-based reporting database"; public branded profiles; configurable workflows ([S31]). Symplectic's own quick-start guide: Elements suggests author identifiers (ORCID, Dimensions, Scopus, ResearcherID, arXiv, figshare, SSRN) which the user approves or rejects; it then "automatically retrieve[s] publications … and place[s] them in the 'Mine' or 'Not Mine' folders"; name-based hits go to *Pending* and the user is emailed; the user claims/rejects individually (tick/cross) or in bulk; delegates may "impersonate" a researcher; manual entry has "automatic checking to confirm you do not create a duplicate" and "Assisted Entry" from CrossRef/Google Books by title, DOI or ISBN; "Required fields are marked with an *" ([S32]).

**DSpace-CRIS (4Science).** Open-source CRIS managing "researchers and groups, departments and organisational units … projects … publications and patents" that can "Exchange information with external systems and databases (ORCiD, PubMed, WoS, etc.)" ([S33]). DSpace 7.3's ORCID integration, back-ported from DSpace-CRIS, lets users "connect their local DSpace profiles with ORCID, showing an authenticated ORCID badge where appropriate and pushing DSpace records to their ORCID profiles" ([S34]). Wiki documentation (fetch blocked, HTTP 403; quoted from search excerpts): "During submission and workflow, potential duplicates are presented and feedback from the submitter and validator are collected via deduplication alerts", with merge tooling for CRIS objects since 5.10 ([S35]); ORCID push runs "automatically over the night or manually", queued changes "can be manually discarded or immediately pushed by the researcher", and the researcher sets "which information needs to be sent and how/when" ([S36]).

**VIVO.** An open-source linked-data platform that can "automatically connect data from your institution with external sources of data on researchers, scholarly activities, funding and impact", supports self-editing profiles and visualisations ([S37], [S38]). Wiki (403; excerpts): "Self-Editor users only have permissions to edit their own VIVO profile"; ingest options are the Harvester, Karma and XSLT ([S39], [S40]). No claim/reject or validation-state model is documented publicly.

**Haplo Repository.** Researchers self-deposit "via online forms or by importing existing records using DOIs" with "different metadata records for different types of output"; managers are alerted, records "can be returned for revisions", publication is automatic on approval, with an audit trail; metadata is also pulled from Datacite with de-duplication ([S41]). Reports are built on a standard framework and administered under "Reporting administration" ([S42]).

## 3. Design / UX guidance that applies

**Nielsen's 10 heuristics** (NN/g, [S43]): 1 visibility of system status; 2 match between system and real world ("speak the users' language"); 3 user control and freedom ("emergency exit"); 4 consistency and standards; 5 error prevention; 6 recognition rather than recall; 7 flexibility and efficiency of use (shortcuts, bulk); 8 aesthetic and minimalist design; 9 help users recognise, diagnose and recover from errors ("plain language, precisely indicate the problem, and constructively suggest a solution"); 10 help and documentation. For data-heavy apps NN/g adds that generic spinners fail when "waits exceed 10 seconds", that live previews prevent errors, and that accelerators (bulk actions, shortcuts) serve expert users ([S44]). RIMS mapping: heuristic 1 = the researcher sees the output's workflow state on their own list; 2 = use ORCID/CASRAI vocabulary; 3 = withdraw a submission; 5 = DOI lookup before typing; 7 = bulk claim/reject; 9 = field-level validation messages.

**WCAG 2.2 AA** (W3C Recommendation, 12 Dec 2024, [S46]). Most relevant to forms, tables and data apps: 1.3.1 Info and Relationships (A) — table headers and form labels programmatic; 1.3.5 Identify Input Purpose (AA) — autocomplete on name/email; 1.4.3 Contrast (Minimum) (AA); 1.4.10 Reflow (AA) — no horizontal scroll at 320 px except data tables; 1.4.11 Non-text Contrast (AA) — input borders, focus rings, status chips; 2.1.1 Keyboard (A); 2.4.6 Headings and Labels (AA); 2.4.7 Focus Visible (AA); 2.4.11 Focus Not Obscured (Minimum) (AA, new in 2.2) — sticky headers must not hide the focused row; 2.5.8 Target Size (Minimum) (AA, new) — 24×24 px for claim/reject icons; 3.2.6 Consistent Help (A, new); 3.3.1 Error Identification (A) — "the item that is in error is identified and the error is described to the user in text" ([S47]); 3.3.2 Labels or Instructions (A); 3.3.3 Error Suggestion (AA); 3.3.4 Error Prevention (Legal, Financial, Data) (AA) — reversible or confirmable submissions; 3.3.7 Redundant Entry (A, new) — previously entered data "auto-populated, or available for the user to select" ([S48]), which is exactly what ORCID/DOI pre-fill delivers; 3.3.8 Accessible Authentication (Minimum) (AA, new) — ORCID OAuth satisfies this; 4.1.2 Name, Role, Value (A); 4.1.3 Status Messages (AA) — save/queue confirmations "programmatically determined through role or properties … without receiving focus" ([S49]).

**GOV.UK Design System.** Validation: "Do not validate when the user moves away from a field. Wait until they try to move to the next part of the service", always validate server-side, add "Error: " to the page title, and redisplay the form with the user's data intact ([S51]). Error summary: "Always show an error summary when there is a validation error, even if there's only one", placed above the `<h1>`, focus moved to it, each message linking to its field and worded identically to the inline message ([S50]). Task list: use when users "do not want to, or cannot, complete all the tasks in one sitting" and can choose order; statuses such as *Completed* and *Incomplete* shown as tags ([S52]). Tag: for status of items that "can have multiple states"; "Use adjectives … and not verbs"; "do not use colour alone to convey information"; never make tags interactive ([S53]). Check answers: for small-to-medium transactions, with "Change" links carrying hidden context text, action-specific button text such as "Accept and send" ([S54]). Table: "Use the table component to let users compare information in rows and columns", captions as headings, `scope` on header cells, numbers right-aligned, never for layout ([S55]).

**USWDS.** Tables: `<th scope="col">`/`scope="row"`, sortable columns via `data-sortable` and `data-sort-value`, stacked responsive variant with `data-label`, sticky headers for long lists ([S56]). Forms: mark required fields with an asterisk and explain it at the top, group with `<fieldset>`/`<legend>`, keep DOM order equal to visual order, align error text with its field, avoid disabled controls ([S57]). Tag: "Users frequently confuse tags as buttons"; "Don't mix interactive and static tags"; ARIA live regions for dynamically loaded content ([S58]). Complex-form pattern: establish trust, progress easily, keep a record; "Allow the users to save and resume", use a step indicator, show "questions on one micro-topic at a time" ([S59], [S60]).

**Jakob's Law** (NN/g): "Users spend most of their time on other sites. This means that users prefer your site to work the same way as all the other sites they already know" ([S45]). Applied here: the ~185 researchers already use ORCID (required by CIÊNCIAVITAE sync and FCT) and CIÊNCIAVITAE. Mirror their vocabulary and sections: ORCID's record has *Works*, *Employment*, *Funding*, *Peer review*, and visibility choices "Everyone / Trusted parties / Only me" ([S10]); CIÊNCIAVITAE has *Produções*, *Projetos* and "Público / Semi-público / Privado" ([S12]). Call outputs "Works/Produções", affiliations "Employment/Percurso profissional", the add action "Add works", and the public flag "Visibility", so no new mental model is required (heuristics 2 and 4, [S43]).
